# Автозагрузка продаж из xMark Analytics + планы по территориям ПФО

**Дата:** 2026-09-20
**Статус:** дизайн на согласовании
**Источник требований:** `C:\Users\MARS\Desktop\xmark-api\ИНСТРУКЦИЯ.md` (+ `swagger.json`, 361 метод),
файл плана `C:\Users\MARS\Desktop\Татарстан План 2026.xlsx`, уточнения пользователя в сессии 2026-09-20.

---

## 1. Зачем

Сегодня данные о продажах попадают в анализатор так: человек руками выгружает файл
из xMark Analytics (продукт ЦРПТ, данные МДЛП) и загружает его в систему. У xMark
есть официальный REST API — значит выгрузку можно не делать руками.

Три цели, в порядке ценности:

1. **Планы 2026 и выполнение к ним.** Сейчас в кабинете нет плана по ПФО на 2026 —
   не с чем сравнивать факт. Файл с планом есть.
2. **Загрузка продаж без файлов** — кнопка «Загрузить из xMark за период».
3. **Общие данные для команды.** Выгрузка грузится один раз и видна всем сотрудникам
   группы «PFO Sonin», каждый фильтрует свою территорию.

---

## 2. Что мы НЕ делаем

Границы важны, потому что учётная запись xMark — общая с живым сотрудником
(Сергей Сонин, региональный менеджер), а система государственная.

- **Не трогаем настройки в кабинете xMark**: экспорт данных (разделитель CSV, шаблон
  имени файла), сохранённые фильтры Сонина, выгрузки на FTP `edi.pharmc.ru`
  (там живой обмен, предположительно с дистрибьютором).
- **Не используем файловые выгрузки** (`custom_actions/run`) в регулярной работе:
  каждая занимает 1 слот из 10, общих с сотрудником. Регулярная загрузка идёт через
  `POST /api/disposal/list`, который слоты не тратит.
- **Не удаляем чужие задачи** в разделе «Выгрузка данных».
- **Не расширяем лимиты и не просим отдельную учётку** — схема рассчитана на то, что есть.
- **Не строим разграничение доступа** на этом этапе (решение пользователя: «пока всё,
  потом ограничим»). Все сотрудники группы видят все цифры ПФО.

## 3. Три этапа

Каждый этап даёт видимый в кабинете результат и проверяется отдельно.
**План реализации пишется отдельно на каждый этап**, а не на все три сразу: этап 2
опирается на решения, которые станут известны только после этапа 1 (фактическая схема
`drug_prices`, заполненность `employees_data.email`).

### Этап 1. Цены и план 2026 (xMark не нужен)

Почему первым: не зависит от внешнего API и паролей, а результат виден сразу.

**1.1. Привести `drug_prices` к одному виду.**
Сейчас таблица описана в трёх местах по-разному:

| Где | Колонки |
|---|---|
| `migrations/0000_public_the_phantom.sql:48` | `drug_id, price, currency, valid_from…` |
| `server/adminRoutes.ts:236,253` | `drug_name, price_per_unit` |
| `server/index.ts:1242` + клиент `src/data/salesData.ts:73` | `drug_pattern, drug_label, price_per_unit` |

Клиент считает рубли по `drug_pattern` + `price_per_unit`. Значит это и есть целевая
схема; админка должна писать в неё же. Первый шаг реализации — посмотреть фактическую
схему в боевой базе и выровнять код под неё. Без этого «внести прайс через админку»
либо упадёт, либо запишет цену туда, откуда её никто не читает.

**1.2. Заполнить `drug_prices` каталожными ценами.**
Источник — `server/catalogSeed.ts` (он же `src/types/sales.types.ts`): 12 препаратов
с ценой за упаковку (Артоксан таб. 320 ₽ … Драстоп Адванс 1176 ₽).
Численно ничего не изменится: при пустой таблице код уже падает обратно на эти цены
(`salesData.ts:69`). Смысл в другом — цены становятся редактируемыми из админки,
и появляется одно место правды.
Проверка: в консоли `[SharedData] Обновлено из БД: N строк, 12 цен` (не «0 цен»).

**1.3. Ввести понятие «территория».**
Осторожно с именами: таблица `world_medicine.territories` в проекте уже занята —
там регионы внутри округа. Новая сущность называется **`sales_territories`**:
территория ответственности сотрудника = имя + список регионов.

```
sales_territories        (id, name, district_id, created_at)
sales_territory_regions  (territory_id, region_name)
```

Из файла плана заводим:

| Территория | Регионы |
|---|---|
| Татарстан | Республика Татарстан, Удмуртская Республика |
| Марий Эл-Чувашия | Республика Марий Эл, Чувашская Республика |

Факт по территории = сумма её регионов. Привязка «сотрудник → территория» в этом
этапе не делается (нужна только для разграничения доступа, отложено).

**1.4. Загрузить план 2026.**
Файл `Татарстан План 2026.xlsx`, один лист, три блока в упаковках:

| Блок | Строки | За год |
|---|---|---|
| ОБЩИЙ ПЛАН ПФО | 2–14 | 576 126 упак. |
| Татарстан | 18–30 | 191 839 упак. |
| Марий Эл-Чувашия | 34–46 | 47 240 упак. |

В каждом блоке 12 препаратов × 12 месяцев + итог за год. Названия препаратов
совпадают с каталогом, но с висячими пробелами («Артоксан гель ») — нужна нормализация
через существующий `normalizeDrugName`.

Существующая таблица `regional_plans` хранит план на **один регион**
(`user_id, year, region_name, product_id, month, plan_units`) и для территории из
двух регионов не годится: делить 191 839 упаковок между Татарстаном и Удмуртией нечем.
Поэтому новая таблица:

```
territory_plans (id, year, scope_type, scope_id, product_id, month, plan_units, source, updated_at)
  scope_type: district | territory
  scope_id:   pfo | sales_territories.id
  source:     откуда пришёл план (imported_xlsx | manual) — чтобы ручную правку
              не затёр повторный импорт файла
  UNIQUE (year, scope_type, scope_id, product_id, month)
```

Импорт — скриптом `scripts/import-territory-plan.ts`, идемпотентным (повторный запуск
обновляет, а не дублирует). Импорт через UI не делаем: файл разовый, формат нестандартный.

Проверка: сумма импортированного за год совпадает с колонкой «на год» из файла по
каждому блоку, ИТОГО ПФО = 576 126.

### Этап 2. Кнопка «Загрузить из xMark»

**2.1. Модуль связи с xMark** — `server/xmark/client.ts`:

- `login()` → `POST /api/login` с `{ email, password }` из `.env`
  (`XMARK_EMAIL`, `XMARK_PASSWORD`), возвращает токен-UUID;
- токен уходит в заголовке `Authorization` **без слова `Bearer`** — особенность xMark,
  с `Bearer` вернётся 401;
- один логин на прогон, не в цикле: учётка общая, и неизвестно, не выбивает ли новый
  вход активную сессию сотрудника (см. риски);
- `readDisposals(token, from, to)` → постранично `POST /api/disposal/list`,
  `pageSize` 1000, признак конца — страница короче `pageSize` (общего счётчика в ответе нет).

**2.2. Перевод полей** — `server/xmark/mapping.ts`, чистая функция без сети,
поэтому тестируется без обращения к боевой системе:

| xMark | Колонка нашего CSV |
|---|---|
| `date` | Дата документа |
| `federal_district` | Федеральный округ |
| `federal_subject` | Субъект федерации |
| `area` | Район |
| `city` | Город |
| `partner_org_name` | Наименование организации |
| `med_product_prod_sell_name` | Название ЛП |
| `med_product_auto_name` | Комплексное наименование ЛП |
| `cnt` | Количество |
| `exit_type` | Тип выбытия |
| `partner_type` | Тип организации |
| `branch_address` | Адрес |

Суммы в рублях xMark не отдаёт — выручка считается по `drug_prices` (этап 1).
Обработчик это уже умеет: при отсутствии колонки суммы пишет в лог
«конвертация в рубли будет через прайс-лист» (`fileProcessor.ts:163`).

**2.3. Встраивание в существующий конвейер.**
Загрузчик пишет полученные строки во временный CSV с теми заголовками, которые
`detectColumnMapping` уже распознаёт, и передаёт файл в `processCSVFileStreaming`.
Ни одна строка работающей логики не меняется: COPY, агрегация, `upload_history`,
прогресс-бар, статусы — всё как при обычной загрузке файла.
Альтернатива (писать из API прямо в `raw_sales_rows` своим COPY) отклонена: это копия
существующей логики, которую придётся чинить в двух местах.

**2.4. Эндпоинт и кнопка.**
`POST /api/xmark/import { from, to }` — только для ролей `admin`, `director`, `manager`.
На экране «Загрузка данных МДЛП» рядом с загрузкой файла появляется кнопка
«Загрузить из xMark» с выбором периода.
Период по умолчанию — **последние 30 дней**, а не «вчера»: xMark дозаливает данные
задним числом (`update_date` бывает свежее `date`), и загрузка только за вчера
навсегда оставит прошлые недели неполными.
Повторная загрузка пересекающегося периода **заменяет** прежнюю, а не складывается
с ней: перед вставкой деактивируются прошлые xMark-загрузки того же периода
(механизм `is_active` в `upload_history` уже есть).

**2.5. Общие данные группы.**
В `upload_history` добавляются `scope VARCHAR(20) DEFAULT 'user'` и `scope_group VARCHAR(100)`.
xMark-загрузка помечается `scope='group'`, `scope_group='PFO Sonin'`.
Чтение данных: пользователь видит свои загрузки **плюс** загрузки групп, к которым
относится. Связь пользователя с группой — по e-mail между `users.email` и
`employees_data.email` (таблица расширена колонками `crm_group, position, city, email,
hierarchy_level`, см. `adminRoutes.ts:151`); при отсутствии совпадения — запасной
вариант по ФИО `users.name` ↔ `employees_data.employee_name`.
Фактическую заполненность `employees_data.email` надо проверить по базе до реализации —
если поле пустое у большинства, основным ключом становится ФИО.

**2.6. Внятные ошибки.** На 401 — сообщение «Вход в xMark не прошёл, вероятно сменился
пароль» в `upload_history.error_message` и в интерфейс. Молчаливый отказ недопустим:
в проекте уже был случай, когда выписка из CRM не грузилась шесть дней, потому что
ошибку никто не видел.

### Этап 3. Ночной автомат

Включается только после того, как пользователь сверит цифры кнопки с привычной ручной
выгрузкой. Запуск в 5:00 (днём сотрудник работает руками, тяжёлые запросы ему мешают),
скользящее окно 30 дней, результат — запись в `upload_history` и уведомление об ошибке.

## 4. Модель доступа (этап 2)

Решение пользователя: **пока все сотрудники ПФО видят все цифры округа**, фильтр
территории — удобство, а не ограничение. Сотрудник ставит фильтр по своим регионам и
сохраняет его, кабинет открывается на его территории, итог по ПФО остаётся виден.

Что это значит технически: `scope='group'` снимает изоляцию по `user_id` **только для
чтения общих загрузок**. Изоляция личных загрузок (`scope='user'`) сохраняется без
изменений. Разграничение по территориям — отдельная задача, когда будет известно,
кто за какую территорию отвечает.

## 5. Тестирование

TDD, тесты пишутся до кода:

- **`mapping.ts`** — на фикстуре из реального ответа `disposal/list`: все колонки на
  местах, висячие пробелы в названиях препаратов срезаются, пустой `area` не роняет строку.
- **Импорт плана** — на реальном файле: суммы по месяцам сходятся с колонкой «на год»,
  повторный запуск не создаёт дублей.
- **Пагинация** — на заглушке HTTP: три страницы по 1000 + хвост 340 дают 3340 строк,
  один вызов `login`.
- **401** — заглушка отдаёт 401, проверяется текст ошибки в `upload_history`.
- **Живая проверка** — вручную, на одном дне, после согласования с пользователем.

## 6. Риски и открытые вопросы

| Риск | Что делаем |
|---|---|
| **Новый вход может выбить сессию сотрудника** — вендором не описано, не проверено | Проверить вживую до включения автомата: Сонин остаётся в кабинете, мы логинимся, спрашиваем, не выкинуло ли. Если выбивает — только ночной запуск и предупредить человека |
| Максимальный `pageSize` не подтверждён (проверено на 5 и 20) | Начать с 1000, при обрывах снижать |
| Пароль от xMark был передан в переписке открытым текстом | Пользователь меняет пароль и кладёт новый в `.env` сама; `.env` в `.gitignore` |
| Смена пароля молча ломает загрузку | Понятная ошибка на 401 (п. 2.6) |
| Схема `drug_prices` расходится в трёх местах | Этап 1.1 — выровнять по клиенту |
| `employees_data.email` может быть не заполнен | Проверить по базе; запасной ключ — ФИО |
| Цены каталожные, а не из реального прайса | Пользователь подтвердила, что цены те же. Заменяются из админки без правки кода |
| Остальные территории ПФО не описаны | В файле только две; остальные добавляются по мере появления данных |
